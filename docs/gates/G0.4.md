## Context loss, teardown, and fallback decision

Both backends were forced through `WEBGL_lose_context`, restored, and rendered at frozen t=2. Before/after **1920×1080 screenshots were byte-identical**: zero changed pixels and maximum channel delta zero. Phaser's owned resource generation advanced 1→2 and recovered four textures, seven VBOs/VAOs and one program; the same static CPU geometry and retained texture sources repopulate GL resources.

Three subsequent complete game/renderer destroy/recreate cycles each left exactly **one canvas and one live instance** (`created,destroyed` = `2,1`, `3,2`, `4,3`). Owned resource counts stayed fixed; custom GL buffers, VAOs, textures and programs are explicitly deleted. No browser errors were captured. After forced GC, final Phaser used heap was 13,423,784 bytes versus 12,740,072 before the three cycles; backing storage changed only +6 bytes. Pixi used heap was 11,756,748 versus 11,651,200, backing storage +11 bytes. Small JS/cache variation is reported, not hidden as a zero-allocation claim; this finite lifecycle check does not prove an unlimited-duration heap soak. The tested owned GPU resources and DOM/game lifecycle show no accumulating leak.

Phaser-specific rendering code is bounded: the `SoldatMap` class is approximately 223 formatted lines, with a small documented Extern framebuffer binding; texture preparation/shaders are shared with the fallback. Pixi's public adapter is approximately 165 class lines. Its Geometry vertex-count implementation assumes a four-byte backing view for interleaved stride; a Float32Array byte owner preserves the exact 20-byte layout while the color attribute remains `unorm8x4`. No engine edit is required for that adaptation either.

**Choose Phaser:** fixture fidelity and frame headroom are indistinguishable at this workload; the modest public-API size advantage in Pixi does not outweigh removing the requested Phaser scene/input/audio shell. Keep `pose.ts` isolated and promote the map/part transforms with the sim render-view integration, rather than replacing them with stock Mesh2D tint interpolation or Phaser's NPOT-refusing texture-wrap method.

## Source findings to carry into SPEC/PLAN

No SPEC.md or PLAN.md edits were made by this lane. Integration should record this scoped result and retain the unexercised laptop qualification.

1. **Map `(0,1)` is not a normalized bottom-left image anchor.** `GfxSpriteVertices` calls `GfxMat3Transform`, whose actual matrix is `T(tx,ty)·T(cx,cy)·R·T(-cx,-cy)·S`; its `(cx,cy)` is an absolute rotation center. Edge `(0,0.5)` has the same semantics. Gostek's separate `DrawGostekSprite` uses normalized centers scaled by image dimensions. Treating scenery `(0,1)` as an image origin initially caused 3.9–13.7% screenshot differences; using the original matrix reduced them to the passing table above. See `reference/opensoldat/client/Gfx.pas:1371-1409,2304-2316` versus `GostekGraphics.pas:176-207,435-483`.
2. Terrain uses direct RGBA8/UV vertex copies, vertex-stage color PMA and source-over blend: `Gfx.pas:532-560,793-796`; texture premultiplication is performed exactly once at GPU upload from the importer's straight-alpha PNGs. This clarifies SPEC §4.2/4.3 ordering.
3. Edge selection/geometry, gradient and layer ordering follow `MapGraphics.pas:460-492,617-749` and `GameRendering.pas:990-1086`; sector exclusion/point tests follow `PolyMap.pas:442-486,604-637`. The browser fetches raw PMS sector metadata because render JSON intentionally omits it.
4. The source include contains **131 definitions**, not 138; the earlier research counted text lines. The extreme UV claim also needs the map-versus-corpus correction above.

This evidence establishes fidelity to the pinned **OpenSoldat** renderer. It is not a pixel-identity claim about proprietary classic Soldat 1.7.1.1.
