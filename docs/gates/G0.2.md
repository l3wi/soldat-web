## Reproduction commands

From the repository root (macOS arm64, Xcode installed):

```sh
brew install fpc
/usr/bin/time -p ./sim/build/setup-toolchain-macos.sh
./sim/build/.toolchain/bin/compile -iV
# 3.3.1
./sim/build/.toolchain/bin/compile -Twasip1 -Pwasm32 -iTP
# wasm32
./sim/build/spike/build.sh
./build-out/spike/spike-native
# 14f981d5915d020b
node packages/sim-host/src/node.ts
# runtime=v24.14.0, ticks=10000, hash=14f981d5915d020b, stateBytes=384, stdout=""
shasum -a 256 build-out/spike/spike.wasm
wc -c build-out/spike/spike.wasm
```

`setup-toolchain-macos.sh` installs into gitignored `sim/build/.toolchain`; its source checkout defaults to a short `/tmp/soldat-fpc-bcd7288-macos-src` path. It preserves the user's Homebrew compiler. Darwin's FPC driver intentionally looks for `ppcwasm32`, whereas `crossinstall` installs `ppcrosswasm32`; the setup script installs the required backend-discovery symlink, without modifying compiler sources. All spike source units are rebuilt (`-B`), with separate native-target and WASM PPU directories.

Linux/CI (requires sufficient Docker VM free disk):

```sh
/usr/bin/time -p ./sim/build/build-image.sh --no-cache --progress=plain
docker image inspect soldat-web/fpc:bcd7288 --format '{{.Id}} {{.Size}} {{.Architecture}}'
docker run --rm -v "$PWD:/work" soldat-web/fpc:bcd7288 ./sim/build/spike/build.sh
# Individual compiler invocations:
docker run --rm -v "$PWD:/work" soldat-web/fpc:bcd7288 fpc -Twasip1 -Pwasm32 [options] source.lpr
docker run --rm -v "$PWD:/work" soldat-web/fpc:bcd7288 fpc [options] source.lpr
```

Supplementary Linux builds used `-e SPIKE_OUT=/work/build-out/spike-linux` so artifacts did not replace the primary local outputs. For Linux amd64, pass `--platform linux/amd64` to `build-image.sh`; this path is unmeasured here. The multi-stage image retains full native RTL/FCL/packages, cross RTL/packages, C/C++/Clang, CMake, git, OpenSSL/protobuf development files, PhysFS development files, Python and build tools for the native oracle.

## Spike scope and host ABI

`SpikeCore.pas` creates ten active particles: five Euler and five Verlet particles, different inverse masses, gravity, damping, four ordered constraints per system, and deterministic sinusoidal forcing. It calls original Vector and Calc helpers (sqrt, vector length/normalize, Angle2Points/arctan), plus Pascal sin/cos. `Game.pas` supplies only the upstream `Grav: Single = 0.06`. Spike-only PhysFS reports no files and raises on attempted file reads; no gameplay file path is pretended to work.

Exports are `spike_reset`, `spike_step`, `spike_run(ticks)`, `spike_state_ptr`, `spike_state_len`. Thin declarations must live in the Pascal `library` itself: exports of routines declared only in another unit were silently absent in the first attempt. This backend behavior and the toolchain build flow were learned from [humanova's MIT-licensed recipe and WebExports.inc](https://github.com/humanova/soldat-web/tree/31bb3d5cb0eaa2eefd20b205b646feb8ba9c92fd); the full reused-work notice is in `sim/build/NOTICE`.

The 384-byte state buffer is 96 little-endian f32 values: Euler particles then Verlet particles, five each, with nine values per particle (`pos.x/y`, `velocity.x/y`, `oldPos.x/y`, `forces.x/y`, `inverseMass`), followed by six probes (`Vec2Length`, angle, sin(angle), cos(angle), normalized x/y). FNV-1a-64 hashes every byte in that buffer; signed i64 JS returns are normalized with `BigInt.asUintN(64, ...)`. The TS host exposes the exports, state-bit reads, imports and captured stdout; `--trace` on the native/Node runners emits tick/hash/all 96 f32 bit patterns for divergence diagnostics.

The linked RTL imports 28 WASI functions. The host supplies empty argv/environment, zero clock/entropy, stdout/stderr capture, standard-stream metadata and explicit BADF/NOTCAPABLE/NOSYS errors for unsupported filesystem/poll operations. Unknown imports fail loudly. No host time or randomness enters particle inputs. No C imports or objects are present.
